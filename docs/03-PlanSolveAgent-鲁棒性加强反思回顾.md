# PlanSolveAgent 本轮鲁棒性加强反思回顾

## 一、背景与目标

本轮改造的核心目标是：

1. **对齐 Python 版本能力与接口习惯**，使 TypeScript 实现在使用体验和行为上更一致。
2. **提升 PlanSolveAgent 在真实 LLM 输出波动下的稳定性**，重点解决计划解析（`Plan.ts`）容易受模型输出格式影响的问题。
3. **统一项目内 Agent 实现风格**，降低后续维护成本。

---

## 二、本轮改动概览

### 1) `ReflectionAgent.ts`：从“独立类”升级为“项目标准 Agent 形态”

主要变化：

- 继承 `Agent` 基类，统一与 `ReActAgent` 的架构风格。
- 构造函数改为对象参数形式：`name / llm / systemPrompt / config / maxIterations / customPrompts`。
- 保留并实现 Python 版核心链路：`initial -> reflect -> refine`。
- 支持早停条件：
  - 中文：`无需改进`
  - 英文：`no need for improvement`
- 将最终结果写入消息历史：`user` + `assistant`。

结果：

- 对外 API 更一致，后续集成成本更低。
- 兼容中英文反馈，提升可用性。

---

### 2) `PlanSolveAgent.ts` + `Executor.ts`：对齐 Python 版结构并接入项目基类

主要变化：

- `PlanSolveAgent` 改为继承 `Agent`。
- 新构造方式支持 `customPrompts`，可独立覆盖 `planner`/`executor` prompt。
- 任务流明确化：
  - 先规划（`planner.plan`）
  - 若空计划则早失败并给出明确提示
  - 再执行（`executor.execute`）
  - 最终写入消息历史
- `Executor` 支持 prompt 注入，增强可配置性。

结果：

- Agent 实现风格统一。
- prompt 维护更灵活，便于后续实验不同策略。

---

### 3) `Plan.ts`：解析鲁棒性重点加强（本轮核心）

这是本轮改造中最关键的一步，我把思考过程拆成了三个问题：**为什么做、怎么做、结果如何验证**。

#### 为什么要做（问题识别）

在真实调用中，我们发现 Planner 的失败并不总是“模型不会规划”，而常常是“模型会规划但输出格式不稳定”：

- 理想情况下模型会返回 JSON 数组；
- 但实际常见输出还包括：markdown 代码块包裹、单行数组字符串、编号列表、夹杂解释文本的列表等；
- 旧逻辑对格式较敏感，一旦 parse 失败就会得到空计划，后续 Executor 无法启动。

例如同一个问题“帮我制定一次前端性能排查计划”，模型可能返回以下几种格式：

- 示例 A（标准 JSON，最理想）：`["采集性能基线", "定位瓶颈模块", "制定优化方案"]`
- 示例 B（代码块包裹）：
  ```json
  ["采集性能基线", "定位瓶颈模块", "制定优化方案"]
  ```
- 示例 C（编号列表）：
  1. 采集性能基线
  2. 定位瓶颈模块
  3. 制定优化方案
- 示例 D（混合解释文本）：
  `建议按以下步骤执行：- 采集性能基线 - 定位瓶颈模块 - 制定优化方案`

这些输出语义上都“可用”，但如果解析器只接受一种格式，就会把“可恢复问题”误判为“任务失败”。

这意味着系统主要风险不在“能力上限”，而在“输入波动下的脆弱性”。因此目标从“解析正确”升级为“**在输出波动下尽可能提取可执行计划**”。

#### 怎么做（方案设计与取舍，结合代码实现）

我采用了“**分层解析 + 统一清洗 + 可观测日志**”的策略，而不是继续强化单一 JSON 解析。对应代码主要落在 `src/agent/plan-solve-agent/Plan.ts` 的 `parsePlan`、`normalizeSteps` 与 `plan` 三个方法。

1. **分层解析（由强到弱）**

- **第一层：优先解析 fenced code block**
  - 入口：`extractCodeBlockContent(text)`
  - 关键实现：使用正则匹配 ```json / ```javascript / ```js / ```python 代码块内容。
  - 解析：把代码块内容交给 `tryParseJsonArray(candidate)` 做 `JSON.parse`。
  - 对应策略标记：`strategy: "codeblock-json-array"`

- **第二层：解析原文 JSON 数组**
  - 入口：`tryParseJsonArray(raw)`
  - 目标：覆盖“模型未包代码块，但直接输出 JSON 数组”的场景。
  - 对应策略标记：`strategy: "raw-json-array"`

- **第三层：一行数组字符串兜底**
  - 入口：`raw.match(/^\[(.*)\]$/s)`
  - 逻辑：匹配后按逗号切分，再逐项去引号。
  - 对应策略标记：`strategy: "fallback-one-line-array"`

- **第四层：按行级列表兜底**
  - 入口：`raw.split("\n")`
  - 逻辑：逐行 trim 并过滤空行，交给清洗函数统一处理。
  - 对应策略标记：`strategy: "fallback-line-list"`
  - 说明：此层会附带 `reason: "未匹配到合法 JSON 数组，按行级列表兜底解析"`

这四层是“从结构化到非结构化”的降级链路：前层失败才进入后层，尽量保证语义可恢复。

2. **统一清洗（确保可执行）**

这部分由 `normalizeSteps(steps)` 负责，重点是把“提取到的文本”转换成“可执行步骤数组”：

- 使用 `.replace(/^[-*\d.\s)]+/, "")` 去掉 bullet/编号前缀（如 `-`、`*`、`1.`、`1)`）；
- 使用 `.replace(/^['"]|['"]$/g, "")` 去掉步骤两端引号；
- 过滤空字符串（避免出现空步骤）；
- 使用 `Set` 去重并保持顺序（防止重复执行同一步）。

例如输入：`["1. 采集性能基线", "采集性能基线", "", "- 定位瓶颈模块"]`，清洗后会得到：`["采集性能基线", "定位瓶颈模块"]`。

3. **可观测增强（便于排障）**

在 `plan(question, options)` 中，我把“模型输出”和“解析路径”都显式打日志：

- 先打印原始输出：`console.log("✅ 计划原始输出...")`
- 再打印解析策略与步数：`console.log("✅ 计划解析成功（${strategy}）...")`
- 若走兜底分支会打印解析说明 `reason`
- 若最终计划为空，会打印错误日志并附带 `{strategy, reason}`

这样在排查时可以快速判断：

- 是模型完全没输出（`empty-output`）
- 还是模型输出了但格式偏移（走 fallback）
- 还是解析规则仍覆盖不足（空计划 + reason）

这里的关键取舍是：**宁可多做一层安全兜底，也不要把可恢复的问题直接升级为任务失败**。

#### 结果是什么（效果与结论）

改造后的直接效果有三点：

1. **空计划率下降**：面对非标准输出时不再立即失败，而是能通过后续层级提取步骤；
2. **执行链路更稳定**：Planner 更少中断，Executor 能更连续地拿到可执行计划；
3. **定位效率提升**：通过 `strategy/reason` 日志，能快速判断是“模型输出偏移”还是“解析覆盖不足”。

总结来说，这次改造把 `Plan.ts` 从“格式依赖型解析器”升级成了“面向波动输入的恢复型解析器”，对 Agent 端到端稳定性是一次结构性提升。

---

## 三、为什么这波加强是必要的

在 Agent 场景中，规划模块通常是后续执行链路的入口。一旦规划解析失败，会直接触发：

- 执行阶段不可用（空计划）
- 错误传递到业务层（看起来像“Agent 随机失效”）
- 难以定位（此前日志无法区分“模型问题”与“解析逻辑问题”）

因此，这次针对 `Plan.ts` 的强化，本质上是对 **系统抗波动能力** 的建设，而不仅仅是“解析函数优化”。

---

## 四、做得好的地方

1. **先统一架构，再补能力**：先对齐 `Agent` 基类风格，再做鲁棒性增强，避免后续重构返工。
2. **优先做高杠杆改动**：把重点放在规划解析入口，收益覆盖全链路。
3. **保留可配置空间**：`customPrompts` + 可注入模板，兼顾稳定与可实验性。
4. **补齐观测信号**：策略与原因日志提升问题定位效率。

---

## 五、仍存在的不足

1. **缺少自动化测试覆盖**
   - 目前鲁棒性逻辑主要靠代码审查与手动推断验证。
   - 尚未为不同输出形态建立固定回归用例。

2. **错误恢复仍偏“静态”**
   - 当计划为空时目前直接终止，尚未尝试“自动重试+纠偏提示词”。

3. **类型约束可进一步增强**
   - 当前 `parsePlan` 返回结构是运行时约定，可进一步引入更严格 schema 约束。

4. **提示词与代码的职责边界仍可优化**
   - 解析兜底较多时，可能掩盖了 prompt 质量问题；后续可双向优化。

## 六、可落地的下一步计划

### P1（优先）

1. **补 `Plan.parsePlan` 单元测试**（覆盖至少 8~12 个典型输入）：
   - fenced json
   - raw json
   - one-line array
   - markdown list
   - 编号列表
   - 混合噪声文本
   - 空输出
   - 重复步骤
2. **失败场景引入一次自恢复重试**：
   - 当计划为空时，自动追加“只输出 JSON 数组”的纠偏指令重试 1 次。

### P2（增强）

3. **接入结构化输出能力**（可复用 `Agent.runStructured` 思路）：
   - 让 planner 优先走 JSON schema 约束输出。
4. **增加执行阶段质量守卫**：
   - 对每步结果做最小有效性检查，必要时触发局部重试。

### P3（工程化）

5. **沉淀统一 Agent 模板**：
   - 将 `constructor/run/logging/history` 的通用模式抽象为约定，减少新 Agent 样板差异。

---

## 七、结论

这轮加强的价值不在“改了多少代码”，而在于完成了三件关键事情：

1. **能力对齐**：TS 与 Python 版本在核心行为上达成一致。
2. **稳定性提升**：规划入口对模型输出波动更不敏感。
3. **可维护性提升**：实现风格统一、可配置性更好、日志更可排障。

整体上，这是一轮对 Agent 工程质量非常“值回票价”的改造。下一步只要补齐自动化测试与失败自恢复机制，就能把当前成果从“可用”进一步推到“可靠”。
